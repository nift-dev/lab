02 / architectures

Two source models. One publication.

The distinction is intentional: the agent-primary pipeline has less transformation work because rendered HTML is maintained source.

HUMANS + AGENTS

docker

Keep the authored source.

  1. Maintained Markdown Frontmatter + structured CLI/API sources
  2. Docker compatibility renderer Standalone Goldmark / Chroma + bounded ports
  3. Transient HTML Generated bodies, never the editorial source
  4. Nift composition Raw HTML + shared layouts + explicit dependencies
  5. Publication + search Minification, downloads, metadata, feeds, Pagefind
AGENTS IMPLEMENT / HUMANS DIRECT

docker-agent

Maintain the rendered content.

  1. Maintained HTML Rendered bodies + associated typed metadata
  2. Nift composition Raw HTML + shared layouts + explicit dependencies
  3. Publication + search Downloads, metadata, feeds, Pagefind

No routine Markdown renderer, generated-reference transformation or HTML minification stage. These are the maintained-HTML architecture’s disclosed boundaries.

A Docker compatibility layer, bounded by evidence.

The human renderer implements the pinned corpus’s required shortcode/include behavior and seven render-hook categories, backed by real Docker fixtures. It does not attempt to recreate Hugo generally. Literal template/Nift-like syntax survives raw composition; mount and published-path normalization are explicit.

These timings are standalone compatibility rendering plus Nift orchestration/composition, not native \@markup performance. The two pipelines are not equivalent authoring-model benchmarks.

04 / profiling

The expensive work surrounded the Markdown.

Raw Markdown parse/render was well under a second in the original human pipeline. Shared shell, repeated HTML analysis and minification explained much more of the total.

REUSE

Prepare shared structure once.

Navigation values/adjacency and invariant branches are reused. Templates are read once; generated route HTML is no longer retained in a large Python cache. Human shell preparation fell from 16.19 to 2.68 s; agent preparation from 15.62 to 3.53 s.

ANALYZE

One body parse, two outputs.

A shared four-worker analysis supplies heading bindings and Markdown downloads. Forced full builds still analyze/export all 2,170 pages. Export writes are now small because parsing/conversion is measured in joint analysis, not omitted.

BATCH

Keep minification. Remove repetition.

Eight human minifier workers and a bounded, exact-input SVG cache preserve output bytes. Minification fell from 19.78 to 1.81 s. YAML reuse, safe C-backed loading and Chroma lexer reuse also reduce compatibility overhead.

Precise invalidation pays off.

Human body edits compile exactly 1, 10 or 100 changed pages. Footer, navigation and title edits compile zero bodies. A title change no longer rerenders all 2,170 pages: its whole median fell from 71.30 to 9.20 s. Footer fell from 47.44 to 16.27 s; navigation from 54.63 to 13.95 s.

Small edits are still search-limited.

One- and ten-page medians are slightly higher than the original migration in both projects. Full/shared-input gains do not mean every edit improved. Fresh search is retained, and these later active-desktop samples show higher indexing costs. Initial values and all ranges remain in the evidence.

The retained Hugo changed-input runs are full production CLI publications. They are not Hugo development-server hot reload. No claim is made that Hugo lacks development caching, or that these Nift edits beat its unmeasured server workflow.

06 / maintenance

Choose what you want to maintain.

Build time matters, but the maintained representation determines editing, review and ownership.

323shared chrome templates
4.55 MBshared chrome source
4.27 MBsame published JS in both

Both use explicit route, navigation and metadata models and preserve Docker’s frontend interactions. The ten published JavaScript files total 4,266,240 bytes in each project; these are uncompressed totals, not per-page downloads. A simpler build does not mean less shipped JavaScript.

docker

Conventional editorial source.

Markdown/frontmatter remain familiar; readable diffs and structured CLI/API sources retain their authority. The source tree preserves useful Docker organization.

The responsibility

A Docker-specific compatibility layer, more transformation work and runtime dependencies. New corpus behavior requires a real fixture and a bounded port. Explicit family/route/metadata bindings and retained frontend assets must stay coherent.

docker-agent

Rendered HTML as source.

3,902 maintained HTML page files, including setup/auxiliary files, for 3,901 published documents. Agents edit rendered bodies directly; normal builds omit Markdown and source-derived reference generation.

The responsibility

Keep associated metadata, navigation and export state coherent. Specialized references are maintained rendered output. There is no conventional Markdown authoring workflow; human direction and review still matter.

Human routine tooling adds safe PyYAML, standalone Goldmark/Chroma/GoAT and pinned minification libraries. Agent routine builds use Python’s standard library, Nift and Pagefind. Both retain compiled upstream frontend assets; changing the frontend/tooling remains a separate engineering responsibility.

07 / assessment

What would this agent maintain?

An explicit engineering assessment from working on both implementations. These preferences are not measurements of long-term productivity or editing reliability.

01 / AGENTS IMPLEMENT, HUMANS DIRECT

I would choose docker-agent.

For routine agent-led maintenance, removing content and generated-reference transformation makes the operational pipeline easier to reason about. Explicit HTML, shared structures and metadata mappings are workable for agents, and the materially smaller full-build cost makes repeated publication checks cheaper.

I would accept the duty to update related metadata and references coherently. Large source representations are manageable, but they still need review and parity/lifecycle gates.

02 / HUMANS AND AGENTS BOTH EDIT

I would choose docker.

Markdown/frontmatter and structured CLI/API sources make ordinary human contributions more familiar and reviewable. I would keep those authoritative inputs rather than ask people to maintain rendered reference HTML. The optimized whole build is already below this experiment’s measured Hugo production pipeline.

The bounded compatibility code is a real maintenance cost. I would accept it for the demonstrated corpus, while requiring fixtures for new behavior and clear ownership of frontend/tooling changes.

03 / BOTH ALREADY EXIST; NO MIGRATION DECISION

The same source-model preference holds.

If both implementations were already accepted, with equally available required services, I would maintain docker-agent for agent-only implementation under human direction, and docker for mixed human+agent editing. This preference excludes migration effort and incumbency; it follows the ongoing maintenance responsibilities.

We did not measure total agent cost, human editing effort or long-term productivity. Build feedback is only one part of the maintenance loop.

08 / official migration

Worth a serious engineering evaluation.

Would this justify Docker investigating an official Nift migration? My assessment is yes. It does not establish that Docker should definitely migrate.

AGENT JUDGMENT

The benefits are substantial enough to investigate.

The preserved-Markdown implementation improved full publication time and measured process/phase RSS while preserving the accepted corpus and tested browser behavior. Dependency-aware shared-input builds and successful route lifecycle checks make this more than a throughput demonstration.

The next decision belongs to Docker’s engineering workflow: weigh compatibility ownership, new-content discovery/validation, frontend regeneration, CI/deployment integration and moving away from an established Hugo toolchain. The smaller operational architecture of maintained HTML is attractive only if that authoring model fits.

I would propose a scoped engineering evaluation, with real contributor edits, frequent upstream changes and Docker’s actual CI/container deployment and service integrations. Production certification, team ergonomics and ongoing maintenance cost remain to be demonstrated. Performance alone does not establish universal superiority or justify an unqualified platform switch.
