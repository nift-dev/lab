Independent Nift experiment. Not endorsed by Deno. Nift itself was not modified. This is a faithful migration, not an approximate redesign.

02 / architectures

Two sources. One publication.

The representations are intentionally different. The human path derives publication outputs; the agent-primary path maintains them.

Nift deno / Authored-source / Human + agent

Author the source. Derive the rest.

  1. Markdown/MDX, frontmatter + structured references AUTHORITATIVE
  2. Corpus-bounded standalone renderer DERIVE
  3. Transient verified HTML CACHE
  4. Nift raw composition + explicit dependencies
  5. Publication + search / LLM / download derivation

Authored source organization, components and structured references remain editable. Generated HTML is disposable. Missing/corrupt cached outputs recover; source, renderer, metadata and toolchain changes invalidate verified derived work.

Nift deno-agent / Rendered-source / Agent-primary

Maintain the publication representations.

  1. HTML + explicit metadata/download/search/LLM projections AUTHORITATIVE
  2. Nift raw composition + explicit dependencies
  3. Publication

No routine Markdown/MDX/JSX content renderer and no Deno runtime in normal publication. The smaller build trades derivation for coordinated source maintenance: the same edit may touch HTML, downloads, retrieval projections and metadata.

The renderer ports only behavior required by the pinned corpus; it does not reconstruct a general Lume framework. These are complete orchestrated pipelines, not native Nift @markup performance measurements. OG images and compiled frontend assets are maintained publication inputs in both migrations.

Developers and agents usually change a small part of a site. Iteration speed often matters more than cold full-build speed.

What profiling removed, and what remains

Repeated component-directory inventories and shared metadata expansion were removed. Explicit input/output hashes allow reuse of deterministic pages and search/LLM exports. Four persistent DOM-only workers preserve the original parser, serializer and table wrapping; small edits avoid worker startup. There was no per-page MDX/JS subprocess to eliminate.

Cache corruption, missing ancillary outputs, metadata removal, layout removal against native Lume, aliases and literal template-like code were checked. Conservative shared-input invalidation remains. Search still uses a whole-stage key. Narrower invalidation, less shell/DOM work, lower prepared-reference memory and cheaper selected-image metadata preparation are future profiling targets.

The authoring model requires derivation, but not this exact DOM/layout implementation. There is no defensible claim that the entire remaining gap is unavoidable “Markdown tax”, or that it demonstrates a Nift core limit.

07 / memory

Less time, with a memory tradeoff.

Maximum measured process/phase RSS. These figures are not aggregate concurrent process-tree memory.

Deno DOM workers are threads in the renderer process and contribute to its measured RSS. Diagnostic serial/two/four-worker runs were 22.36s / 887.1 MiB, 15.32s / 1,330.2 MiB and 13.51s / 1,485.8 MiB. They are tuning observations, not headline medians. Four workers favor elapsed time and consume more memory.

The final human forced range reaches 2,107.5 MiB; the earlier cold campaign reached 2,225.8 MiB. Those peaks remain visible. A faster human renderer is not a claim that runtime machinery has disappeared.

08 / maintenance

Build simplicity is not source simplicity.

The faster project has less transformation work. The more conventional source model has fewer publication representations to keep coherent.

Nift deno / Authored-source / Human + agent

Consistency from authoritative source

  • Markdown/MDX/frontmatter and structured API/reference inputs remain authoritative.
  • One source derives downloads, search and LLM projections.
  • Human-readable edits and diffs reduce opportunities for those outputs to drift.

Costs to own

Renderer/layout/reference compatibility, derivation runtime, conservative shared-source invalidation and explicit prepared-input refresh tooling.

Nift deno-agent / Rendered-source / Agent-primary

A very small publication pipeline

  • About one second for measured forced/fresh publication.
  • No routine Markdown/MDX renderer or Deno content runtime.
  • Maintained HTML composes directly through Nift.

Costs to own

Agents must keep HTML, Markdown downloads, search/LLM projections, metadata and navigation coherent. A body-hash acknowledgement detects an unacknowledged edit; it does not prove semantic consistency across representations.

Coordinated source editing is outside timed publication. Lower build time is not a measured claim of lower total maintenance effort.

09 / assessment

Codex’s maintenance choice: Nift deno.

This corpus’s ancillary publication contract changes the judgment. Faster maintained HTML is useful, but source consistency matters more here.

Here, Nift deno is the authored-source human+agent migration repository, nift-experiments/deno. Nift deno-agent is the rendered-source agent-primary migration. Upstream Deno/Lume is the original implementation. The preference below is for the Nift authored-source migration.

Does a 1.31s unchanged publication and a 4–6s common body-edit loop make the human-oriented source model cheap enough to prefer its stronger source consistency?

Agents implement, humans direct

Preferred: Nift deno (authored-source migration)

Yes, for this experiment. Common body edits already have a short feedback loop, while one authoritative source derives downloads, retrieval and LLM outputs. That consistency outweighs the additional build cost. Navigation/metadata/lifecycle edits are slower and remain part of the decision; neither those costs nor agent projection-editing effort is hidden.

Humans and agents both edit

Preferred: Nift deno (authored-source migration)

Markdown/frontmatter and structured inputs are easier to author and review. Editors do not manually synchronize the same fact across several maintained publication forms. The measured iteration loop makes that source model practical during routine work.

Both already exist; migration effort removed → unchanged

If migration effort and incumbency are removed, I still prefer the Nift authored-source deno implementation for both agent-led maintenance and mixed human+agent editing. The preference follows the ongoing source-of-truth contract and incremental feedback, not sunk migration effort or incumbency. Dropping/redesigning the ancillary requirements could change the agent choice, but would change this parity experiment.

10 / official evaluation

Worth a serious engineering evaluation.

The agent believes the evidence justifies Deno evaluating an official migration from Lume to Nift. It does not establish that Deno definitely should migrate.

Full publication, common-edit iteration, measured memory and fresh reproducibility are strong enough to justify a scoped engineering evaluation. Keeping human-friendly authoritative source while publishing unchanged in about 1.3s and common body edits in 4–6s is a practical maintenance benefit, not just a cold-build graph.

An official decision must test real contributor edits and CI/deployment: adapter ownership, structured-input acquisition/refresh, frontend regeneration, Orama/search/backend/service boundaries, editor ergonomics and integration with Deno’s ecosystem. Broad invalidation and memory peaks remain useful targets. Performance alone does not certify production integration or establish universal superiority.

11 / init review

The migration tooling was part of the experiment.

nift init --migration provided a useful operating framework. The corpus supplied the details it could not invent.

Initialization preserved existing AGENTS.md, supplied baseline-first/parity/checkpoint guidance and safely refused a rerun on an existing Nift project. The generated playbook was useful; AGENTS/HANDOVER alone were not a sufficient migration specification.

Useful future scaffolds

Baseline manifest; source-ownership table; dependency/cache inventory; divergence ledger; checkpoint/status table; distinct cached/forced/application-cold sample schemas.

Guidance exposed by real work

Metadata-removal tests; static assets versus generated products; projection coordination; remote-service boundaries; complete publication versus composition-only commands; non-destructive guidance refresh and source-model selection.

These are conceptual improvements for later tooling work, not Nift changes made during this migration or a general Lume implementation.

12 / methodology

Keep the qualifications in reading distance.

The host, retained inputs and external-service boundaries are part of the result.

Host and samples
Intel i7-12700H, 20 logical CPUs, 64 GiB RAM, Linux 7.0.0-29. Active desktop; OS caches/user workload uncontrolled. Five serialized samples per headline mode; alternating migration model order where practical. Medians and min–max ranges, not confidence intervals.
Tools and source
Nift 4.8.0 unchanged; Deno 2.9.7; pinned denoland/docs revision 9e5dd8d930c8734defe1c3172986e6312353ac1c. Measured migration code: deno 380baeb, deno-agent 4a81df5. Later report/closeout commits contain documentation/evidence only.
Prepared inputs
Dependency installation, acquisition, cloning and source editing excluded. Live std acquisition frozen. Prepared reference JSON/types/std and compiled frontend assets are maintained inputs, with explicit refresh ownership in both migrations.
Native WASM delivery
Repeated native timing locally delivers exact pinned resvg/esbuild WASM bytes. Original compilation count, worker lifecycle, startup and initialization remain inside timing. Two direct CLI fetch failures and three successful observations remain separate, not pooled. This is qualified production-phase timing, not an unchanged official full-task measurement.
Search and clocks
Human local search/LLM derivation remains measured; agent projections are maintained. Remote Orama relevance/upload/backend not certified. Frozen search/LLM/sitemap clocks are explicit parity inputs, not current production freshness timestamps.
Native non-HTML differences
Every native HTML document matches. Seven path/hash differences are classified: dependency-symlink realpaths change the SDK chunk filename/import while normalized code is identical; search/LLM/sitemap publication clocks differ. The migrations retain the original complete publication bytes.
Memory and counters
Maximum measured process/phase RSS, not simultaneous tree memory. Parsing/Prism/MDX are nested subsets. Parallel DOM/output job-work overlaps main-thread production; do not add it to elapsed wall time.
Validation limits
Documented browser control-state pixel differences are retained; separate interactions pass. Inherited unresolved paths/fragments and duplicate IDs are not silently repaired. Live external services, long-term editing productivity and Lume dev-server latency are unmeasured.
