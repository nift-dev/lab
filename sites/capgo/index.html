Experiment 03 / Capgo / October 2026

One website.
Two migration
philosophies.

What changes when we move a production-scale Astro website to Nift—and then reconsider its implementation for a world where agents do the routine editing?

1,347 routesThree finished implementationsOne pinned production reference

An independent experiment using Capgo’s public website. Not an official Capgo migration or a recreation of its private services.

01 / The premise

Same website.
Different questions.

We compared the original production Capgo / Astro build with two deliberately different Nift implementations. Agent is not simply faithful Capgo with more optimisation. The content and desired behaviour are the reference; the maintenance assumptions differ.

capgo / Faithful migration

How good can a faithful migration be?

Can we migrate a production-grade Astro site without throwing away its authored content model, routes, browser behaviour and existing runtime assumptions?

Fidelity comes first. Keep the existing mental model where practical, reconnect authored MDX/content and metadata, and migrate the build layer. Retain frontend implementation where that is the dependable route to parity.

Humans and agents, working together.

A conventional production codebase: humans engineer and review; agents assist with migration, content, validation and repetitive maintenance.

capgo-agent / Agent-native reconstruction

What if agents perform routine engineering?

Preserve the product, content and behaviour, while reconsidering the implementation around Nift, semantic HTML, CSS and maintained vanilla JavaScript.

Agents can navigate a large corpus, apply repetitive edits and validate many routes. Explicit mappings and deterministic primitives matter more than making every repeated fragment pleasant to hand-edit.

Agents implement. Humans direct and review.

Humans define intent, architecture, policy and acceptance. Source remains inspectable, debuggable, version controlled and reproducible; manual editing remains possible.

This tests a maintenance premise, not whether agents replace engineering judgement. Lower measured build cost does not prove lower long-term maintenance cost.

03 / The process

Start from known-good output.
Recover the structure beneath it.

  1. 01

    A golden reference

    Build the pinned official Capgo site successfully. Capture all HTML, CSS, JS, fonts, images and routes. That production output becomes the canonical oracle, avoiding a screenshot-inspired reinterpretation.

  2. 02

    Faithful → recover the authored site

    Begin with identical compiled output, then extract shared Nift templates, headers, footers and page structures. Reconnect MDX/Markdown, metadata and authored bodies while continuously testing output and route parity. The result goes beyond copying a compiled site into public/.

  3. 03

    Agent → reconsider the implementation

    Use official production Capgo as the visual/behavioural oracle and faithful Capgo as the content/route/source-mapping oracle. Maintain converted HTML and shared Nift structures; recover readable browser controllers and replace the normal Astro build with independent JS bundling.

  4. 04

    Validate, freeze, then measure

    Audit dependencies, test interactions, reproduce a fresh checkout and freeze architecture before repeated benchmarks. A real-edit check caught missing raw-fragment dependencies; explicit Nift declarations fixed propagation before accepting incremental measurements. No optimisation pass followed the final numbers.

What the gates establish

Faithful regenerates 1,343 content/listing/registry heads; four redirect heads remain reference artifacts. All 1,347 parsed heads are byte identical. Its 1,192 accepted body-byte differences pass semantic equivalence.

Agent HTML is byte identical to the reference. Its gate checks retained assets, 21 rebuilt controller entries, 133 generated browser assets and the absence of 103 retired JS files. Both gates report zero introduced semantic/link issues and zero unexpected files.

The reference’s 11,339 existing link/anchor issues remain separately recorded, including missing translated destinations. We preserve upstream quirks rather than silently inventing fixes.

Browser behaviour is a separate check

Thirteen representative page classes at desktop and mobile cover homepage, pricing, product, solution, comparison, docs landing/normal/rich docs, blog listing/article, data, legal and a browser tool. Checks include navigation, dropdowns, tabs, copy buttons, search/filter, TOC, forms, pricing, languages and keyboard/focus behaviour. Actual Algolia search returned results; data-unavailable states matched production.

Of 26 paired viewport screenshots, 18 have no thresholded pixel difference; the remaining differences are below 1%, including animation timing. These are representative viewport checks—not exhaustive full-page pixel or accessibility certification.

What parity does not establish

Real account creation, authenticated workflows, device identifiers, genuine signing success and browser certificate upload/download remain uncertified. External content and availability may change. No accounts or external messages were created. Agent’s allowlisted compatible-provider adapter passes local mock tests; it does not recreate those services. Faithful’s original signing/device endpoints remain unsupported locally, and its older adapter does not automatically reconnect retained controllers.

Corrected Agent revision 6371356 passed an independent fresh clone with no copied project output, dependencies or Nift cache: locked install, first build, all routes, tracked inputs, fragment dependency checks and clean Git status. Installation used an existing npm download cache; this was not a cold-machine package-download test. The preceding bootstrap observation was 5.07 s / 165.4 MiB, excluding installation, and is separate from repeated warm builds.

Simpler build ≠ less shipped JS

Agent has no normal Astro build/runtime requirement or React install, and no Astro hydration islands. DocSearch is a documented Preact compatibility exception for modal, keyboard, focus, ranking and history state. Mermaid, SDK, auth and crypto libraries remain. Production inline controllers and external integrations are explicitly retained, not claimed newly invented vanilla code.

Total rebuilt Agent JS is 6,082,284 bytes, compared with original 6,073,203 bytes: slightly larger. There is no demonstrated overall client-JS reduction. These are uncompressed asset totals, not per-page downloads. All versions retain production CSS/images/fonts.

Inspectable, but substantial

Agent maintains 1,347 wrappers, 1,881 shared HTML includes, 5,990 converted fragments and six templates/helpers. Thirty-seven readable JS files supply all 21 entry controllers. Its locked dependency set has 187 packages and 228,622,975 bytes of installed regular files.

Faithful’s root lock has 188 packages, plus the separate MDX renderer and other inputs; upstream’s Bun monorepo scope differs. Equivalent total install/download footprints were not measured, so no percentage saving is claimed. Agent keeps 19 original CSS files and removes only audited, unreferenced JS from served output.

What would we maintain?

If we were the existing Capgo organisation today

Staying with upstream avoids migration and new certification work, and retains its deployed translation/service system. That is an organisational-risk argument, not a demonstrated development-loop advantage. Team familiarity is unknown, private workflows remain uncertified, and comparable Astro dev/HMR/edit measurements are missing.

If we were committed to Nift, with humans + agents

We would prefer faithful when retaining MDX/content authoring matters. Its captured corpus, source-backed metadata and shared composition are demonstrated; ordinary real-edit family medians are 4.28–6.41 s, with explicit targets at 2.07–3.71 s here. Schema/discovery and new style/asset-generation conveniences still need acceptance or further tooling.

If we were designing for agent-mediated implementation

We would prefer Agent for that premise: explicit source mappings, inspectable markup, readable controllers and parity gates, with normal real-edit family medians of 1.04–1.09 s and targets at 0.86–0.91 s. Those timings support cheap build feedback; they do not measure total validation latency, agent cost or editing reliability. Humans still direct/review, and shared changes require broader builds and checks.

A preference for a Nift engineering workflow and caution about a real production migration can coexist. We cannot decide developer experience from the Astro full build alone.

If migration weren’t part of the equation

Assume all three implementations already exist, are equally production-certified, have equivalent access to the required backends, and the team can work effectively with either stack. Migration, switching cost and incumbency are excluded. The following are engineering preferences based on this corpus, not measured long-term productivity results.

Humans + agents: faithful Nift

We would choose faithful Nift. It keeps authored MDX/Markdown, frontmatter and shared composition readable for people while giving agents explicit mappings and parity gates for corpus-wide work. Measured ordinary real-edit family medians are 4.28–6.41 s and targeted medians 2.07–3.71 s. We prefer that combination of familiar content authoring, programmable preparation and a small measured build budget over maintaining converted HTML by hand.

Astro still provides more complete collection validation/discovery, typed component and scoped-style compilation, and packaged build adapters. Faithful’s bounded adapters and explicit route registration need care; retained compiled browser assets make new browser behaviour and CSS changes less direct to debug and regenerate. Those are real maintenance costs we would accept for this workflow, not capabilities we claim to have finished. Equal backend access removes the worker deployment advantage; translation remains a separate system in either case. Dependency totals are not comparable across the installs, and retained browser libraries remain substantial. Astro edit/HMR was not measured, so this preference does not claim that Nift beats Astro’s day-to-day latency.

Agent-primary: Agent Nift

We would choose Agent Nift. Deterministic source mappings, shared includes and readable controller ownership make routine edits and debugging explicit. Agents can make mapped bulk changes while humans review intent, diffs and acceptance. Its measured ordinary real-edit medians of 1.04–1.09 s and targeted medians of 0.86–0.91 s support repeated build feedback. Independent JS bundling and the absence of a normal Astro build or hydration islands simplify the build architecture; route, dependency, parity and representative browser gates supply concrete checks.

This choice accepts a large fragment corpus and an explicit workflow for new routes, styles and shared changes. It does not imply less shipped JavaScript, fewer total dependencies, exhaustive validation, or proven lower agent cost. Browser SDKs and the DocSearch Preact exception remain. Targets alone do not cover all consumers of shared changes; broader builds and browser checks remain necessary. The documented faithful restoration issue also shows why parity checks belong in the maintenance loop. With incumbency neutralised, we prefer Agent’s inspectable HTML and controller pipeline for agent-led implementation, and faithful’s authored content model for human + agent work.

For shared changes, build the complete affected set and inspect relevant desktop/mobile behaviour. Intentional new content/design requires updating the golden policy, not treating old byte equality as acceptance. We did not measure source-location counts or human/agent effort for these scenarios.

Content: a concrete convenience, not a capability verdict

Upstream’s glob-loaded blog collection declares Zod fields, supported locales, dates and tag normalisation; routes query the collection. Adding a published source entry is discovered by that pipeline. Faithful retains authored MDX/frontmatter and discovers English blog files for listings, but new rendered routes also need body/metadata mappings and Nift registration. Its narrow YAML adapters do not apply the complete upstream collection schema. Agent edits mapped converted HTML and explicitly registers routes.

These are current migration/tooling gaps and different workflows. Nift already composes authored sources, MDX, data, templates and dependencies; a schema validator or route generator can run in preparation. No fundamental content-modelling limitation was demonstrated.

Composition: compare the operation

Capgo uses typed prop declarations, named slots and compiler-scoped styles. Faithful’s registered component adapter already handles parameters, children and named slots; Agent uses shared Nift includes/functions and readable browser controllers. Exact rendered output demonstrates sufficient composition for this corpus. Arbitrary new Astro syntax or freshly scoped CSS is not guaranteed by the bounded migration adapter. Upstream packages that compiler workflow; this is a concrete convenience difference, not proof that Nift cannot compose components.

Localisation: the translation worker does the work

The shared Astro configuration builds English only. Nine advertised language choices point to a separate Cloudflare edge worker, which translates the English origin, stores page/state records, rewrites navigation, language metadata and hreflang, and implements pending-translation retries/fallback. Shared copy is English with generated translation contexts. The Nift versions preserve English output and language links; neither deploys or certifies that worker.

Adding a locale requires changes to web/docs locale definitions and the worker’s supported set/configuration, then deployed validation. We did not measure comparative file counts or effort. The existing worker is an upstream implementation-coverage advantage; the claim that Astro’s i18n model is inherently better for Capgo is withdrawn.

Integrations: turnkey adapters versus programmable seams

Astro’s configured MDX/Starlight, DocSearch, sitemap, icon and Tailwind/Vite packages offer concrete ready-made conveniences. Nift does not require a dedicated framework plugin for each underlying system. Faithful’s hook runs Node content, code and metadata preparation, processes recorded API JSON and consumes generated files with dependency tracking. Agent’s hook independently bundles browser packages with esbuild; its allowlisted provider server composes compatible HTTP services. These are demonstrated orchestration seams.

Algolia, Mermaid, Supabase, metrics, pricing, embeds and browser SDKs connect through ordinary packages, configuration, HTTP or browser code. Translation and signing/device services require separate deployed backends. Retained sitemap/LLM/raw-Markdown assets are not proof of automatic freshness after new content. No inspected integration established an intrinsic inability of Nift to connect; several ports and live workflows remain incomplete. Native/FFI was not exercised and is not counted as evidence here.

Available adapters are distinct from general interoperability. Community size, documentation quality, team familiarity and long-term editing productivity were not quantified. Every identified Nift drawback is classified as an experiment coverage gap, migration tooling gap or different workflow in the source-backed maintenance investigation. It inventories integration families and traces concrete editing operations; no implementation was changed for this reporting correction.

08 / What we learned

Migration is a process.
Maintenance is a choice.

Nift supported a production-scale content migration with high fidelity, without discarding the authoring model. Reconsidering that model around converted HTML and independently maintained controllers reduced the measured build work further.

The benefit is not universal: retained frontend assets, preparation caches, library dependencies and private-service gaps all matter. Agent-mediated editing makes repetitive source representations plausible; it does not remove the need for review, debugging or product decisions.

This work informs future migration scaffolding, source mappings, parity gates and handover support—perhaps a command such as nift init --migration. That is a proposed direction, not an available command.
