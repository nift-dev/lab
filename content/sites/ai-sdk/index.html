03 / islands

Static where possible.
React where useful.

Nift composition does not imply vanilla-only output. The migration retains the interactive parts rather than flattening them.

OPAQUE STATIC CONTENT+INDEPENDENT REACT ISLANDS→HYDRATED PUBLICATION

Real interaction stays

Generation/loading demos, object generation, nested weather, prompts, media/playback, provider/model selection, recipes, tabs/copy, version switching, mobile navigation and search remain interactive.

React islands hydrate around opaque static HTML. The publication does not carry a Next application runtime. Simple content controls use lightweight browser code where appropriate.

Build products have owners

Actual esbuild dependency graphs govern independently cached client, SSR, shared chrome and runtime products. Unrelated content edits preserve island bundles; source/import/toolchain changes invalidate them.

983 mounts in 1,415 content/ancillary sources pass independent host-boundary checks. The content registry is still one eager entry across 16 island families: seven emitted outputs, 1,131,411 bytes. Shared chrome emits approximately 2,035,693 bytes.

Emitted output bytes are not per-page download sizes; each family is not a separate bundle. Deterministic local AI/chat/feedback success/error fixtures verify UI and transport behavior, not live production AI, feedback or analytics. Registry splitting and dependency duplication remain future profiling targets.

06 / profiling

The first faithful build was not the finish.

Parity first → profile → remove redundant work → revalidate → benchmark.

INITIAL / SINGLE DIAGNOSTICS

140.712s authored
91.409s rendered

Faithful, but expensive. Authored MDX compatibility/SSR took 89.101s; Markdown downloads 24.902s. Whole-DOM rendered island refresh took 62.036s.

OPTIMIZED / SINGLE DIAGNOSTICS

53.642s authored
25.673s rendered

Bounded workers and retained reuse; lexical island host spans and batched SSR. These diagnostic runs are not the final five-sample production medians of 83.16s and 37.96s.

Reuse the work that is actually shared

Four bounded workers reuse content-addressed compiled bodies: 201 compilations are reused within 1,386 documents. Metadata, compiler/body and renderer keys are distinct. Version-menu props retain only relevant ancestors/fallback; 5,022 mapping checks match the complete original resolver.

Search is version-scoped, Markdown projections source-scoped and discovery depends on actual projection bytes. Generated products validate input graphs and output hashes.

Keep the rejected experiment

Retaining every unique Shiki HAST/compiled file made things worse: MDX rose to 108.15s and maximum individual process/phase RSS to about 2.49 GiB. That broad cache was rejected.

The accepted design keeps reused bodies only until their last use, with a bounded repeated-input Shiki cache. Rendered island refresh replaces only host interiors rather than reparsing whole documents.

Single diagnostic observations and final campaign medians are different evidence classes. They are not interchangeable optimization percentages. The report and raw history retain both, including failed/interrupted benchmark preparation with no accepted samples.

09 / maintenance

Faster is not automatically preferable.

Choose the maintained source contract, then judge its publication pipeline.

NIFT ai-sdk (AUTHORED-SOURCE)

One authority. Derived projections.

Markdown/MDX/frontmatter and structured versions remain authoritative, readable and easier to review. Downloads, search and LLM references derive from source; retained islands have independent ownership.

Cost: transformation work, a bounded compatibility layer and internal Geistdocs/Fumadocs coupling. Four pinned internal Geistdocs UI modules and one private Fumadocs search reader are explicit maintenance liabilities.

NIFT ai-sdk-agent (RENDERED-SOURCE)

Less transformation. More coordination.

Faster publication and no routine MDX compiler. Agents can maintain HTML directly.

Cost: edits must coordinate HTML, search data, Markdown downloads, LLM references and metadata/navigation. The benchmark excludes the effort of making those changes consistent.

Upstream remains a credible third option.

Next.js/Geistdocs also has authoritative source and stronger native framework, development and deployment integration. The production build measurements do not measure every advantage of that ecosystem.

Fonts and compiled stylesheets are maintained publication assets with explicit update workflows. Homepage statistics and model catalogs are pinned maintained snapshots, while upstream retains public npm/GitHub requests and timeout fallbacks. These architectural differences remain part of the comparison.

Remaining costs are future profiling targets

MDX/highlighting, derived reference work, shared shell SSR, corpus metadata/hash scans, per-version search export and publication copying remain real costs. Navigation legitimately fans out over its tree. Registry splitting, dependency duplication, startup/scan overhead, search granularity and concurrent-memory reductions deserve later investigation. They do not reopen this accepted experiment.

10 / opinion

An explicit three-way judgement.

Codex assessed Upstream Next.js/Geistdocs, Nift authored-source and Nift rendered-source—not the repo name in isolation.

AGENTS IMPLEMENT / HUMANS DIRECT

Preferred: Nift ai-sdk
(authored-source)

One authoritative source, lower coordination burden, independently retained islands and much lower measured publication time/memory than upstream. The additional transformation cost is acceptable for consistency.

HUMANS + AGENTS BOTH EDIT

Preferred: Nift ai-sdk
(authored-source)

Markdown/MDX/frontmatter and structured sources are easier to edit and review. The rendered-source speed does not outweigh the stronger source-of-truth model.

REMOVE MIGRATION EFFORT + INCUMBENCY

Codex still prefers Nift ai-sdk (authored-source) in both maintenance scenarios.

This accepts the bounded adapter burden for the demonstrated publication architecture. Upstream is credible when native development/deployment integration takes priority; the experiment does not fully measure that tradeoff. Official adoption still requires a deployment/backend pilot.

11 / official

Worth evaluating. Not a migration decree.

The evidence justifies Vercel evaluating a migration from the current Next.js/Geistdocs AI SDK docs application to Nift composition with retained React islands.

Why investigate seriously

Complete production publication is materially faster with lower measured memory, while maintaining authored content and real interactive islands. Controlled production edits, complete output coverage and fresh-clone reproduction make this an engineering result worth testing in a real deployment.

What a production pilot must resolve

Host/runtime deployment, process rollover, private API credentials, AI/chat/feedback/search integration and analytics. Local fixtures do not certify those services. Internal module coupling, maintained asset/snapshot updates and native Next tooling must enter the decision.

A serious deployment/backend evaluation, not an unconditional recommendation. Build performance alone does not establish that Vercel should migrate the official site. The external playground remains separately hosted.

12 / guidance

The islands lesson is discoverability.

Dogfooding nift init --migration did not reveal a framework prohibition.

Generated guidance already permits React, Vue, Svelte and other tools. What needed stronger visibility was island composition and explicit ownership of client/SSR products, dependencies, emitted bytes and invalidation.

Future guidance should make “the lightest faithful solution” concrete: Nift composes the publication; neighboring tooling owns useful interactive islands. It should distinguish maintained assets from derived products, authoritative versus coordinated source models, remote-service evidence, pinned versions and full/cached/fresh build scope.

13 / methodology

Keep the boundaries in view.

A production benchmark is useful when readers can see exactly what it includes and excludes.

Commands + pinned inputs

Upstream: pnpm --dir apps/docs build:site, including sync, Fumadocs and Next production build. Migrations: python3 scripts/build-content.py (forced for full modes), including preparation, bundling, Nift, reference outputs, search and asset/runtime publication.

Node 24.21.0, pnpm 11.23.0, Nift 4.8.0. Upstream keeps its pinned eight-CPU Next setting; authored MDX uses four bounded workers. Six public external image responses are frozen. No private credentials or real backend submissions.

Sampling + state

Five serialized samples for each of three modes and workflows, rotating project order: 45 accepted publications. Active host; OS cache state uncontrolled. Fresh application state clears generated application caches/products, keeps maintained assets and installed packages, and is not machine cold.

Dependency installation, state-reset/archive preparation, input mutation and verification are excluded. Input-case observations are single runs, not distributions.

What is not measured

Next dev-server/HMR, source-editing/review labor, deployment transfer, host/process startup, production backend latency or private AI/feedback/analytics integration. Local deterministic fixtures establish a narrower UI/transport contract.

Preview robots keep Disallow: /; production indexing policy needs deployment configuration. Runtime changes require the deployment runtime to roll over.

Accounting + limitations

Individual process/phase RSS and approximate sampled descendant RSS sums differ. Nested Shiki/task counters are not additive. Phase medians need not sum to pipeline medians.

Next’s build/runtime artifacts and standalone public/runtime files have different transport inventories; raw file-count equality is not claimed. Coverage and output hashes are established by separate parity gates.
