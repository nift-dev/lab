11project/diagnostics/

Where Nift spends the work.

Profiles point to both filesystem-specific amplification and a busy scalar/value execution path.

P0 · CORRECTNESS

One call must mean one call.

The read-loop execute(...).stringify() reduction prints CALLED three times; binding the result prints it once. Accepted adapters use the checked safe binding. This is a serious core defect, not an accepted benchmark failure.

P1 · METADATA

Reuse what the tree already knows.

The inspector queries status and file size even for type-only checks. Extra 20,000 stat calls accompany the 10k explicit-stat workload. Preserve races, symlinks and error contracts when consolidating.

P1 · ALLOCATION

5,578,191 allocations.

The separate 10k stat heaptrack diagnostic records 1,111,623 temporary allocations. String construction and condition trimming are concrete leads; instrumentation changes timing.

P1/P2 · SCALAR

Bytes become evaluator work.

Read profiles include AST evaluation, RuntimeValue lifetime, loop dispatch and variable lookup. Bulk reads are far less extreme. This motivates decomposition, not a claim that one function explains the gap.

Template Engines also profiled expression/string/allocation work; Concurrency profiled AST/value handling while demonstrating real multicore scaling. A shared value/execution mechanism is plausible, but their differing paths do not establish a single root cause.

12project/practitioner/

Would I choose it?

Usable for bounded Nift-owned automation; large-tree throughput is weak in this snapshot.

For new filesystem or release tooling today, I would choose Python for compact library-driven automation or Go for a maintained standalone utility. Traversal overhead, repeated metadata queries, allocation volume, slow per-byte interpreter work and copy/mirror costs are operational problems. Missing timestamps, native cryptographic hashing and clear recursive cleanup add real contract gaps. Exactly-once side-effect reliability takes priority over speed.

What would change my preference?

Reusable metadata-bearing directory entries; fewer status/size queries; substantially less path/string/value allocation; faster scalar processing; native SHA-256 and timestamps; safe recursive helpers; repaired chained-call evaluation; and competitive large-tree scaling. I would retain explicit roots, artifact ownership, lifecycle and independently checkable outputs.

Existing Python or JS module requirements remain specific integration reasons to choose those runtimes. This Linux campaign does not certify Windows paths, symlinks or portability. Explicitness is useful only when the runtime reliably enforces it.

13project/method/

Frozen evidence. Open interpretation.

No measurements, adapters or diagnostics were changed to produce this redesign.

AMD EPYC 7642 / Ubuntu 24.04.4 / kernel 6.8.0-134 / ext4 / 4 vCPU, 8 GiB. Four-CPU affinity. 77 scenarios / 752 supported cells / 14,264 measured observations + 752 warmups.

Fresh timing includes launch and exit; booted timing begins after readiness and ends at the complete response. Every observation uses a new runtime. Fixtures are restored, fully read and statted outside timing. Runtime order rotates; no outliers are removed. Full result sets/output SHA-256 checks and independent distribution/reset audits pass. Low-count stress tails are descriptive.

Warm Linux filesystem state, ASCII paths, fixed three-level corpus, no symlink/permission/glob or physical-bandwidth claim. Five file sizes (96–2,048 bytes) and extensions correlate with groups. No fsync or global cache dropping. Output serialization is inside timing; canonical oracle sorting is outside (Nift ls itself sorts).
