Equivalence before speed

The output has to contain the page.

Every build checks the complete corpus route set and each page’s exact title/heading and expected body. Hugo raw HTML is enabled; Astro uses file routes; VitePress has a minimal custom theme, retains hydration assets and generates one extra validated 404 page.

Fresh-fixture builds (raw mode application-cold) recreate the entire project fixture; shared pinned node_modules/toolchains and their generated dependency cache remain prepared across the series. Astro/Vite’s shared node_modules/.vite cache is inventoried. This does not measure a complete reset of all application caches. Warm full removes generated output/cache directories while retaining other application build state. Both are full builds; neither is a machine-cold boot. Nift uses one build thread; Hugo GOMAXPROCS=1; process affinity is one logical CPU.

One warmup plus five measured samples per cell, rotating tool order. C-supervised fork/exec-to-exit latency excludes Python/supervisor launch. Kernel waited-child RSS is a high-water metric, not simultaneous aggregate tree memory; concurrent children/shared pages require a separate accounting boundary.

Old results are incomparable. Corrected Hugo content, minimal VitePress theme, route parity, application state and direct timing change the old workload. Schema-4 used sampled aggregate RSS with a 10 ms polling loop. No historical speedup is claimed.

Observation → interpretation

A small build surface is useful evidence.

Different preparation, rendering, bundling and hydration paths appear in these costs, while their features are mostly unused by minimal pages. Nift also has a broader scripting/build role than a conventional SSG. The fixture does not exercise complex Markdown/MDX, assets, component graphs or maintained production websites.

Warm full names the retained-state workflow, not an expected speedup. Official totals do not isolate individual phases. A separate all-core diagnostic below supplies bounded filesystem/profile evidence, not a precise phase-time decomposition. Scaling describes this fixture. Competitor incremental server/HMR behaviour was not measured; comparing it to Nift’s one-shot dependency build requires a new equivalent experiment.

Nift used about 27% less fresh wall time and 44% less warm wall time here. Fresh ranges overlap (Nift faster in four of five matched rounds); warm ranges do not overlap. Nift’s fresh total CPU time was slightly higher despite its shorter wall time. CPU/wall can exceed 100% with parallel workers; this is aggregate child CPU divided by wall time, not a worker-count measurement.

Separate 50 ms process sampling found median maximum target OS-thread counts of five for Nift and seven for Hugo, with one product process each. OS threads are not simultaneously active workers. Sampling and GNU-time controls are separate from the headline cohort; their wall clocks include observer/polling overhead. A separate second-host default-fresh subset measured Nift 1.089 s and Hugo 1.461 s, versus 1.194 s and 1.636 s above; hosts are not pooled.

Untimed fixture accounting found 10,001 additional Nift internal files totaling 6,584,541 bytes beyond public HTML. Both systems produced the expected 10,000-page semantic corpus; Nift HTML totaled 1,317,780 bytes and Hugo 1,327,780 bytes (one extra newline per page). Nift’s tracked JSON/templates and Hugo’s Markdown/frontmatter pipeline do different parsing and metadata work. This byte count does not identify a millisecond share of the fresh gap.

The observed Nift fresh–warm difference was 390.725 ms. Exact-source inspection and separate strace runs support a retained-metadata mechanism: identical internal files can be checked and have timestamps refreshed rather than recreated atomically. Public HTML is removed and rewritten in both full-build states. Profiled fresh/warm write counts were 20,002/10,001; warm had more total syscalls, so syscall count alone is not cost. Separate software-CPU profiles had no lost samples; kernel filesystem/path/locking work was visible, while stripped Hugo symbols limit user-code attribution. No precise rendering/GC/metadata time decomposition is claimed.

The historical Hugo fresh median was 5.005 s versus the official final 2.623 s, but the CPU changed from EPYC 7601 to EPYC 7642. A necessary same-node CPU-0 replay of historical/current helpers with the identical Hugo binary measured 2.750/2.645 s, with overlapping ranges. The four measurement/fixture helper files were byte-identical. This does not establish a source-change cause for the historical 47.59% difference; old host/cache state and the exact hardware contribution remain unresolved. Replays used selected wrapper calls, not the complete original four-engine schedule.

Practitioner judgement / AI-DX

Explicit contracts are useful work.

For a conventional human-authored content/theme site, I would choose Hugo where its conventions and existing ecosystem fit. For a human-plus-agent authored workflow, an agent-primary website, or a mixed website/assets/procedural project, I would choose Nift when its APIs and explicit tracking are maintained. Named targets, artifact ownership, input/template mappings and programmable .f policy make intent inspectable; extra metadata is not automatically redundant ceremony.

These are qualitative preferences, not measured authoring/error rates. The harness checked complete routes, semantic contents, full-rebuild parity and unchanged unrelated pages; those checks are not universal product-native guarantees. This campaign did not compare Hugo incremental recovery or establish comprehensive structured build diagnostics for either tool. Parallel throughput strengthens Nift’s case here without erasing the official single-CPU result.
