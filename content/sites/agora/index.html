Agora Docs TanStack Start + Nift

A 2,003-page documentation publication. Keep the interactive application. Rework the build around it.

Agora’s real-time communications platform has a substantial bilingual documentation portal. This experiment preserves TanStack Start, Router, React and authored MDX while changing how content and publication work move through the pipeline.

Independent engineering experiment. Public source pinned before migration. Nift core unchanged. No Agora or TanStack endorsement.

The engineering decision

Our maintenance choice:
Nift + TanStack Start

For maintaining Agora’s documentation, we would choose the Nift-assisted authored-source implementation over the original upstream build workflow.

The unchanged theme/root implementation and matched browser reproduction establish this as an inherited defect, not clean hydration across every theme state. Restoration is checked, not assumed.

Warm and restored outputs retain exact non-HTML bytes. HTML agrees after comparison-only normalization of the Router’s bootstrap updatedAt fields inside its stream-barrier script. Article content and other dates are untouched; production HTML is never normalized. A real upstream highlighting variation is retained in the repeatability evidence.

02 / architecture

A different build workflow. The same framework.

The original portal uses TanStack Start/Router, React, Vite and Fumadocs. Nift takes responsibility for publication composition rather than replacing their runtime.

The project was selected to test a hybrid adoption path: substantial authored MDX, shared components, bilingual navigation, platform variants, OpenAPI references, search and machine-readable exports. Replacing all of this with a static approximation would answer a different question.

Nift agora / authored-source

Keep authored content authoritative.

  1. Maintained Markdown / MDX, frontmatter, includes, navigation and OpenAPI
  2. Independent Fumadocs compilation → cached React ESM + metadata
  3. Derived search, Markdown and LLM projections
  4. Retained Vite / TanStack application + production route SSR
  5. Transient HTML → Nift raw composition → publication

Generated modules and HTML are disposable. Recursive includes, image bytes/dimensions, compiler configuration, source hashes and package revisions participate in invalidation. Editorial dates retain their upstream seed and explicit maintenance workflow.

Nift agora-agent / maintained React ESM

Maintain the compiled representation.

  1. Maintained React ESM articles + explicit catalog/raw/processed metadata
  2. Derived search, Markdown and LLM projections
  3. Retained Vite / TanStack application + production route SSR
  4. Transient HTML → Nift raw composition → publication

No Markdown/MDX article compiler runs during routine publication. The maintained source is React ESM, not HTML-only: shared interactive components still run. Agents must coordinate article modules and their text/metadata representations when editing content.

Fumadocs still supplies content semantics and UI. TanStack still supplies routing and SSR, Vite still bundles the application, and React still renders and hydrates it. These measurements cover the orchestrated pipeline, not native Nift @markup throughput.

05 / optimization

Remove repeated work before tuning Nift.

The improvement came from the combined architecture and its preparation stages.

Separate compilation and publication

Article compilation no longer depends on rebundling the entire application. Valid React ESM and metadata survive ordinary publications. Clean payload paths defer expensive worker/source imports; cached projections are reused when their inputs are unchanged.

Bound work and memory

Compiler workers keep bounded lifetimes and merge metadata deltas once. SSR uses two production workers with bounded route batches and heaps. An immutable shared route plan avoids repeated corpus-wide dependency planning in each batch.

Load only the metadata needed

Compact frontmatter heads and lazy per-document records replace eagerly retaining the full projection catalog in every SSR worker. The complete catalog still exists for exports. Server-only metadata stays out of the public tree.

Preserve correctness while caching

Asset copying checks both source and destination identity and repairs missing/corrupt outputs. Raw source hashes track edits that do not change compiled React. Retirement and restoration gates accompany incremental shortcuts.

OPEN / PRODUCTION

Regional and provider certification

No authoritative new Chinese origin was found; current public Shengwang links still use the legacy origin. Complete regional deployment, provider rule precedence, Accept-negotiated caching and build-image integration remain unverified. The build image must supply Nift explicitly.

The pinned hosting configuration has no explicit cache-header policy, so provider/dashboard defaults cannot be reconstructed from source alone. Four read-only current upstream requests returned correct deep-link HTML, Accept-negotiated Markdown, a Markdown download and a 404; observed responses used public, max-age=0, must-revalidate. This establishes current upstream behavior, not the Nift deployment’s cache correctness. Private Algolia indexing, external-service writes and production API workflows were not exercised. Local Orama fallback was tested. Original CDN assets remain external; this is not a complete offline mirror.

Latest correctness fix is included in reviewed source.

A frontmatter comment can change raw search text without changing the compiled article URL. The authored updater now tracks maintained-source hashes separately. A real YAML-comment test proves correct search updates and exact fixture restoration. This fix follows the captured performance checkpoint and receives no unmeasured speed claim.

08 / maintenance

Our maintenance choice: Nift + TanStack Start.

For this documentation workload, we prefer the Nift-assisted authored-source implementation over the original upstream build workflow.

Our preferred workflow / Nift agora

Keep the application. Maintain one authoritative source.

For maintaining Agora’s documentation, we would choose the Nift-assisted authored-source implementation over the original upstream build workflow. It retains TanStack Start, TanStack Router, React hydration and client navigation while substantially improving observed fresh-build performance and reducing sampled peak build memory.

Dependency-aware publication allows documentation changes to avoid unnecessary application compilation. Markdown/MDX remains authoritative, and search, downloads, metadata and LLM representations are derived together. That is our preference for human maintenance, agent-led maintenance under human direction, and mixed development.

Original upstream / TanStack + Fumadocs

The integrated incumbent

The original workflow is fully integrated with its framework and tooling. The two measured complete production builds require about ten minutes and roughly 5 GiB sampled peak aggregate RSS. We would choose the evaluated Nift-assisted build workflow for maintaining this corpus; this is not a judgement that the application or TanStack is poorly engineered.

Nift agora / authored-source

Our maintenance choice

Retain authored Markdown/MDX, the TanStack application and content functionality. The observed fresh application-state build takes 199.82s / 1,937.1 MiB, with dependency-aware incremental work. One source of truth is easier to review and maintain than coordinated representations.

Nift agora-agent / maintained React ESM

A faster fresh build, more coordination

The fastest observed fresh build is 71.79s / 1,343.0 MiB, but agents must maintain compiled React ESM and coordinated text/metadata records. Similar warm-publication and document-edit costs make that extra coordination less attractive for general maintenance.

The improvement comes from the surrounding build architecture and reduced repeated work. The original TanStack application remains an important part of the preferred implementation. Removing migration effort and incumbency does not change the authored-source preference.

This recommendation concerns the evaluated documentation workload, not every TanStack application. It justifies a serious Nift-assisted TanStack evaluation for Agora; it is not an unconditional migration decree or a claim of certification in Agora’s live infrastructure. Production hosting, services and regional deployment still need owner review.

09 / methodology

Read the boundaries with the numbers.

Source revisions, workloads and memory scopes are part of the result.

Fresh application state
Installed dependencies retained; no generated application/content artifacts. Authored compiles all 1,657 articles. The agent model’s maintained React modules are source, not an unreported generated cache.
Warm forced publication
Valid application/content/projections retained. All required pages are rendered and Nift-composed again; this is not a no-op or fresh-source benchmark.
Process-tree RSS
Same observer sums simultaneously sampled workload-process-group and descendant RSS, excluding the observer/GNU-time wrapper. Shared pages can be counted more than once and short peaks missed. Requested sleep is 20ms; actual intervals are longer. RSS is not peak physical memory or unique-set size.
Individual process RSS
GNU time maximum individual-process RSS is retained separately in canonical samples. It is not interchangeable with the tree-RSS graphs shown here.
Machine and toolchain
Recorded environment: Linux 7.0.0-29 x86_64/glibc 2.43, Node 22.22.1, Bun 1.4.3 and Nift 4.12.0. CPU/RAM were not recorded with the benchmark. A later review-time snapshot reports an Intel i7-12700H, 20 logical CPUs and about 61 GiB RAM; it cannot establish historical load or available memory.
Sampling and provenance
Two accepted upstream production observations; one Nift observation per model/scenario. No additional upstream or repeated final benchmark campaign. Source representation, cache conditions and production-runtime corrections differ; no statistical dominance or universal latency claim.
