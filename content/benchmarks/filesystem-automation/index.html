11project/diagnostics/

Where Nift spends the work.

Historical20261011 profiles and metadata traces below are retained analytical leads, not new final profiles; final exactly-once gates pass.

P0 · CORRECTNESS

One call must mean one call.

The historical reduction printed CALLED three times versus once for a bound result. Finalc14 inline and bound reductions both execute exactly once. The original diagnostic is retained; it is not a current defect.

P1 · METADATA

Reuse what the tree already knows.

The inspector queries status and file size even for type-only checks. Extra 20,000 stat calls accompany the 10k explicit-stat workload. Preserve races, symlinks and error contracts when consolidating.

P1 · ALLOCATION

5,578,191 allocations.

The separate 10k stat heaptrack diagnostic records 1,111,623 temporary allocations. String construction and condition trimming are concrete leads; instrumentation changes timing.

P1/P2 · SCALAR

Bytes become evaluator work.

Read profiles include AST evaluation, RuntimeValue lifetime, loop dispatch and variable lookup. Bulk reads are far less extreme. This motivates decomposition, not a claim that one function explains the gap.

Template Engines also profiled expression/string/allocation work; Concurrency profiled AST/value handling while demonstrating real multicore scaling. A shared value/execution mechanism is plausible, but their differing paths do not establish a single root cause.

12project/practitioner/

Would I choose it?

Usable for bounded Nift-owned automation; large-tree throughput is weak in this snapshot.

Human + agent: Python for new standalone general automation, Go for bulk work, Nift for bounded existing-project operations. Agent-primary: the same conditional choices; explicit ownership/inputs/lifecycle help inspection but autonomous edit/recovery productivity was not measured. For new filesystem or release tooling today, I would choose Python for compact library-driven automation or Go for a maintained standalone utility. Traversal overhead, repeated metadata queries, allocation volume, slow per-byte interpreter work and copy/mirror costs are operational problems. Missing timestamps, native cryptographic hashing and clear recursive cleanup add real contract gaps. Final exactly-once gates pass; side-effect reliability remains essential.

What would change my preference?

Reusable metadata-bearing directory entries; fewer status/size queries; substantially less path/string/value allocation; faster scalar processing; native SHA-256 and timestamps; safe recursive helpers; continued exactly-once reliability; and competitive large-tree scaling. I would retain explicit roots, artifact ownership, lifecycle and independently checkable outputs.

Existing Python or JS module requirements remain specific integration reasons to choose those runtimes. This Linux campaign does not certify Windows paths, symlinks or portability. Explicitness is useful only when the runtime reliably enforces it.
