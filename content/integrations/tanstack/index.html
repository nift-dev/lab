Nift + TanStack

Nift generates the website.
TanStack powers the interactions. Three architectures and 3,000 documents explore how these responsibilities fit together.

Trace the architectures ↓Inspect the original report ↗

The engineering recommendation

Better together.
For this workload.

For this documentation-heavy website with selective interactivity, we’d choose Nift-first with TanStack islands. Full publication is faster, peak build memory is lower, and ordinary articles deliver much less JavaScript.

Adding Nift dependency management to our already optimised Start implementation did not improve this particular workflow. That does not establish the best full-stack architecture. We did not evaluate a standalone Nift full-stack application, and these configurations do not provide identical server-side capabilities.

The control still wins unchanged and individual document-edit builds. These are single observations, and the architectures do not provide identical server-side contracts.

01 / architectures

Who owns the page?

The final comparison contains three 3,000-document configurations. An earlier 62-guide prototype explains how we reached them.

PRELUDE / 62 GUIDES

First, Nift beside TanStack.

The first prototype gave Nift an independent docs shell beside a Start application. It worked, with cheap documentation updates, but separate HTML/JSX layouts and document-to-app navigation added maintenance seams. For that prototype, the assessment preferred the TanStack-only implementation. This smaller, different workload is preserved; its timings are not mixed into the charts below.

Content and behavior before speed.

All 3,000 articles retain their heading text/anchors, table-cell content and highlighted code. Search bytes match the unchanged control; every published local link, image and script target resolves. Browser checks exercise authored/generated MDX tabs and calculators, search, dashboard data, deployment filters/details, capacity controls and saved settings.

A fresh agent fixed Form validation/accessibility from the source map; parent browser checks separately confirmed empty-submit rejection, a stable input label and valid local submission. The API explorer uses real Query loading, Table sorting/filtering and Virtual scrolling—not merely installed packages.

Different inventories, explicit scope.

Nift-first emits 3,089 HTML entry pages, including workspace entry wrappers and the additional explorer. Start configurations emit 3,002 static pages plus runtime application routes. The wrappers are not prerendered dashboards.

The corpus preserves 62 original guides and expands through deterministic fictional, versioned reference generation. It is not 3,000 independently authored production articles. A clean GitHub checkout reproduced all 3,102 publication files byte-for-byte. These are representative functional checks, not certification of every viewport or a production deployment.

03 / measurements

Full publication gets lighter.

Zero-origin linear bars. Each panel states its own axis maximum; compare configurations within a panel.

One observation per case. Not medians. The earlier Phase 2 cohort is retained unchanged, not interleaved with the islands run. Warm publication reuses valid compilation in every configuration; fresh means fresh application state, not a cold OS cache.

Changing ownership removes work.

Nift-first avoids Start/React rendering for ordinary Markdown and whole-document hydration in the browser. Its fresh observation is about 30% faster than the optimised control, with about 31% lower sampled tree RSS. Warm full publication is about three times faster.

Markdown uses a standard Markdown/GFM/highlighting pipeline; MDX still uses the official compiler and build-time React static rendering. The final fresh compilation/rendering stage costs 11.99s. The 979 MDX sources are not free, and these are not native @markup performance results.

What the memory numbers mean

Linux descendant-process RSS is sampled at a 2ms target interval; actual gaps are recorded. The tree peak sums simultaneously resident descendants, can double-count shared pages, and can miss short peaks. It excludes the observer and is neither PSS nor total machine memory. GNU time’s maximum individual-process/phase RSS is retained separately above. No sum of individual maxima is presented as aggregate memory.

06 / lessons

Choose an architecture for the workload.

The recommendation changed after a different ownership model was tested—not after weakening the control.

STATIC / DOCS

Choose Nift-first for this portal.

It is a strong fit when articles dominate and interactive regions are bounded. Faster full publication, lower peak memory and lighter ordinary-page delivery are material here. It does not win unchanged or individual docs edits.

MIXED / INTERACTIVE

Choose the boundary deliberately.

Nift-first combines islands with a bounded workspace in this implementation. The Start configurations retain continuous Router state, shared query context and SSR across the application. Docs↔app document navigation is a tradeoff here, not an inherent limitation of Nift or a verdict on other architectures.

FULL STACK

Full-stack conclusions remain open.

Of the two Start-based configurations tested, the optimised control offered the better measured trade-off. This Nift-first implementation deliberately does not reproduce Start’s server-function lifecycle; fixture-backed JSON is not equivalent. We did not compare a standalone Nift full-stack architecture or establish that Start is generally preferable for full-stack development.

Shared optimisations remain shared.

Isolated MDX compilation, bounded workers, stable bundles and caching helped both Start implementations. They are not exclusive Nift gains. This experiment does not prove that only Nift could implement an efficient static-first site.

Nift-first lets ordinary authors use Markdown, HTML and CSS. A new interactive MDX component still needs an island entry and an explicit fallback/provider boundary. Its simple development watcher requires a manual reload; it does not match the reference’s React HMR experience.

Keep the weaker results visible.

The first islands pass retained the search heap and traversed the graph twice. Correcting those costs helped. A later regression exposed literal-template and failed-intermediate recovery bugs; fixing them added validation cost. The final fresh build is 16.12s, not the faster pre-fix observation.

Future work includes cheaper unchanged planning, incremental search, simpler island registration and better development-server integration. Those are future Nift/tooling targets, not reasons to rewrite this result. No Nift core changes were made.
