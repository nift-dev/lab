01 / workflow

One workflow. Three native descriptions.

The common quantitative graph uses identical Python task bodies: content-hashed JSON outputs, text transforms, checks, one real helper compilation/execution, deterministic in-memory packaging and release validation. Additional asset tasks expand the graph. Each successful check produces a receipt in all runners.

Task names model workflow roles. Checks assert known properties of a 32-record input; web/docs transform text; the helper compiles a trivial C program; package validates an in-memory tar. No real TypeScript compiler, application test suite, framework build or deployment is measured.

Cached check receipts are not always-run, outputless checks. This is a synthetic single-project workflow—not a production JavaScript framework, package discovery benchmark, or remote-cache comparison. The separate outputless probe appears below.

02 / noop

Nothing changed. State still costs time.

Every task body must remain unexecuted. Nift checks retained tracked input/output state; Turbo and Nx report native local cache hits with output files already present. These are different skip mechanisms, measured as fresh CLI invocations over prepared state. Nx daemon and remote caching are disabled.

07 / failure

A failure blocks descendants, not independent work.

Semantic certification injects a schema failure, requires a nonzero exit, blocks its descendants and checks independent branch completion. Recovery verifies all expected work and output bytes. These feature tests are separate from successful timing distributions.

Observed failure and retry behavior
RunnerFailure / recovery
NiftNames the failed custom action; independent branches complete. A normal retry reports unfinished build; build --repair is required.
TurboFailed npm task exits nonzero; dependencies-successful continuation permits independent work and blocks dependent tasks. Fix then rerun.

Actual stdout/stderr and start/complete/fail traces are retained with the semantic observations. Exit-code values differ and are not treated as a performance result. Turbo/Nx recovery is tested with full forced execution; Nift uses repair. These tests certify correct retry, not the fastest default incremental recovery path.

09 / inputs

Clean state, cache replay, and outputless checks differ.

All adapters declare own-file/config/body inputs. Nift declares consumed artifact files; Nx hashes dependent task outputs; Turbo propagates prerequisite task hashes through native task dependencies. No hidden wrapper decides which tasks to skip. Separate native capability probes test cases that cannot fairly share the common timing cohort.

Every accepted warmup and sample verifies the exact task-start and completion sets, no duplicates, no failed/blocked work in successful runs, prerequisite completion before consumer start, bounded overlap and deterministic output hashes. 12 / practitioner

Would I actually use Nift as a task runner?

Qualitative practitioner assessment / not benchmark evidence

Yes. I would choose Nift for bespoke authored workflows today when its current APIs cover the job. Its reusable .f policy and explicit artifact contracts are independently attractive; favorable timings are not the only reason. Tracked hooks fit artifact-producing tasks, but cacheable checks currently require success receipts.

Equal performance would not make Turbo or Nx my default for authored workflows. My choice depends on the specific behavior the project needs:

My choice by workflow, including equal performance
WorkflowChoice and reason
Bespoke authored workflowNift: reusable .f procedural policy and explicit action/artifact relationships.
Agent-maintained workflowNift: inspectable ownership, ordering, invalidation and lifecycle contracts support verifiable edits.
Website + assets + native helpers + toolsNift: one project/runtime model when these tasks belong together.
JS monorepo requiring local/remote artifact reuseTurbo: task-result restoration and shared caching with package/workspace pipelines.
Framework-heavy monorepo using Nx toolingNx: project/affected analysis, task inference, plugins, generators and migrations already valuable to that project.

What actually changes my choice?

Turbo: its task-result cache restores declared outputs/logs; remote caching shares those results across developers and CI. These are task-runner capabilities Nift’s retained-state skipping does not provide. Package/workspace dependency and script conventions matter for repositories organized around them. Filtering and persistent/dev-task conventions are usually conveniences for bespoke work; they become requirements where package-aware selection or long-running development tasks are central. Persistent services and remote caching were not benchmarked.

Nx: local/remote computation caching and output restoration are execution capabilities. Project/affected analysis is selection machinery beyond this authored single-project graph. Its plugins infer tasks/inputs/outputs and contribute project knowledge, generators, migrations and executors: a development platform that can save real framework setup and maintenance work. IDE/dev tooling is usually convenience. Nx Cloud distributed CI is a separate multi-machine requirement, not local worker scheduling; it was not measured.

Which Nift gaps matter most?

For my authored-workflow use, I rank native outputless tracked task nodes and declarative environment invalidation first: they affect task semantics and correctness. Local task-result restoration and optional shared remote caching follow; cache-heavy multi-machine projects move them to the top. Next are clean ensure-versus-force targeting, smoother failed-run recovery, then per-invocation workers and graph/query/explain controls. The tested retry uses build --repair. Direct outputless .f checks work but do not themselves supply an incremental parallel outputless DAG.

Artifact ownership, completion order, staleness and lifecycle express different facts. Extra structure is useful when agents can inspect and validate each contract; concise helpers should remove synchronization risks while preserving explicit semantics. Nift need not reproduce Nx’s entire product surface to be a strong task runner.

If those Nift capabilities matured

I would not prefer Turbo or Nx as the default for a new authored workflow if Nift reliably added outputless nodes, environment inputs, local/optional remote task-result caching, ensure-target semantics, worker overrides, graph explanation and smoother recovery while retaining .f programmability. I would still choose Nift for bespoke, agent-maintained and mixed Nift projects.

I could still choose Turbo for package/workspace and persistent-development conventions, or Nx for required project/affected inference, framework plugins, generators/migrations or distributed CI. Those integrations are not automatically supplied by the counterfactual. Existing investment and migration cost can also justify retaining a working tool. These are concrete capability/integration reasons, not an inherent architectural need for a second executor. Reliability and practical fit must be demonstrated, not assumed from a feature checklist.

The accepted results favor Nift strongly, alongside its authoring advantages. They remain synthetic end-to-end observations; the expensive full cells have three measured samples, maximum-child RSS is not summed process-tree memory, and remote caching/Nx daemon-assisted defaults were excluded. This is a qualitative clarification; measurements and measured conclusions are unchanged. A few simple always-run recipes may still favor Just, which was not quantitatively benchmarked.

13 / method

Frozen sources. Retained samples. One node.

One fresh 4-shared-vCPU / 8-GB Ubuntu 24.04 Linode, us-east. CPU affinity includes all four CPUs. Runner order rotates within rounds; scenario order follows a fixed frozen plan. Fresh CLI invocation, prepared local state, no remote cache, Nx daemon disabled. Setup/input mutations are outside the timer; native dispatch, task work and bookkeeping are inside. Stdout/stderr are captured: native status formatting and cache-log costs are included; terminal painting is excluded. Turbo uses errors-only task logs and Nx uses static output. These CLI modes are retained with each command, not presented as equal pure scheduler CPU. No outlier removal.

The mixed body reads the canonical graph for each invocation; that identical cost is included. The suite covers 20/100/1,000 mixed tasks, 100/1,000 tiny tasks, j4 scaling, 100-task j1/j2 full-dirty work and 20-task cache-disabled/targeting cohorts. Failure and unsupported semantics are separate capability tests. Shared-CPU variance, sparse expensive cells and this synthetic single-project model limit generalization.
