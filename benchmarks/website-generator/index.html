Equivalence before speed

The output has to contain the page.

Every build checks the complete corpus route set and each page’s exact title/heading and expected body. Hugo raw HTML is enabled; Astro uses file routes; VitePress has a minimal custom theme, retains hydration assets and generates one extra validated 404 page.

Fresh-fixture builds (raw mode application-cold) recreate the entire project fixture; shared pinned node_modules/toolchains and their generated dependency cache remain prepared across the series. Astro/Vite’s shared node_modules/.vite cache is inventoried. This does not measure a complete reset of all application caches. Warm full removes generated output/cache directories while retaining other application build state. Both are full builds; neither is a machine-cold boot. Nift build_threads=-1; Hugo GOMAXPROCS is unset; every timed process can use CPUs 0–3. Full builds invoke nift build --all; normal incremental builds invoke nift build. These command boundaries are distinct.

One warmup plus five measured samples per cell, rotating tool order. C-supervised fork/exec-to-exit latency excludes Python/supervisor launch. Kernel waited-child RSS is a high-water metric, not simultaneous aggregate tree memory; concurrent children/shared pages require a separate accounting boundary.

Old results are incomparable. Corrected Hugo content, minimal VitePress theme, route parity, application state and direct timing change the old workload. Schema-4 used sampled aggregate RSS with a 10 ms polling loop. No historical speedup is claimed.

Observation → interpretation

A small build surface is useful evidence.

Different preparation, rendering, bundling and hydration paths appear in these costs, while their features are mostly unused by minimal pages. Nift also has a broader scripting/build role than a conventional SSG. The fixture does not exercise complex Markdown/MDX, assets, component graphs or maintained production websites.

Warm full names the retained-state workflow, not an expected speedup. Different totals do not identify individual planning/rendering/cache phases; those were not profiled. Scaling describes this fixture. Competitor incremental server/HMR behaviour was not measured; comparing it to Nift’s one-shot dependency build requires a new equivalent experiment.

Practitioner judgement / AI-DX

Choose the workflow as well as the build time.

For a human-authored existing Hugo/theme estate, I would stay with Hugo when its conventions already fit. For a new human-plus-agent maintained site, an agent-primary site or a mixed procedural publishing project, I would choose Nift when its APIs and explicit tracking fit the requirements. These are qualitative choices, not measured authoring success rates or a universal platform ranking.

Explicit source/output ownership, template dependencies, named targets and .f helper policy can make bounded agent edits easier to inspect. Familiarity to humans and safe agent reasoning are different questions. The measured incremental and targeted paths support practical iteration; the frozen harness checked complete routes, intended contents and full-rebuild parity. Those harness checks are not general product-native guarantees, and equivalent Hugo incremental/HMR recovery was not measured.

Conclusion

Defensible as minimal-page throughput.

The corrected fixture and output gates support this bounded experiment. Its measurement boundaries should travel with every quoted number; read real-site migration reports for architecture and maintenance tradeoffs.
